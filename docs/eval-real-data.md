# 真实数据验证报告（89 封邮件）

> 2026-09-14 · 对真实 163 邮箱 INBOX 全量同步后的抽取表现。
> 这**不是**合成语料的评测（那个在 [eval-report.md](eval-report.md)），
> 而是用真实邮件检验抽取层是否会做出危险动作。

## 为什么要做这一步

合成语料上抽取指标是 100%（召回/精确/F1/自动入历准确率全部满分）。
**在自己写的语料上拿满分，恰恰是最该怀疑的时刻**——语料反映的是我的假设，
不是真实邮件的分布。因此把 89 封真实邮件跑了一遍，逐个人工检查「会被自动
写进日历」的候选。

结果证明这一步是必要的：**真实数据暴露了一个严重缺陷。**

## 发现的缺陷：时间已过的事件被自动入历

### 现象

修正前，4 个被判定为「可自动入历」的候选**全部是过去时间**：

| 抽出的时间 | 来源 | 问题 |
|---|---|---|
| 2026-08-22 07:59 | 阿里云域名到期提醒 ×3 封 | 到期日已过去 23 天 |
| 2026-9-9 15:52 | 中国建筑（香港）合同提醒 | 已过去 5 天 |

这些时间**语义上没错**——邮件里确实写着这些日期。但把过去的时间当作「即将发生
的事件」写进日历，是纯粹的污染。

### 根因

规格只定义了「早于**收信时间** → 待审」，漏了「早于**当前时刻** → 待审」。

对每天增量同步的用户这不会暴露（新邮件的时间通常是未来）。但**首次同步一个
有历史邮件的邮箱**时必然触发——而首次同步正是每个新用户做的第一件事。

### 修复与效果

在评估链最前面加一条朴素比较：`start < now` → 待审。
放在所有其它检查之前，因为**无论置信度多高、来源多可靠，过去的时间都不该
自动写进日历**。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 可自动入历候选数 | 4 | **0** |
| 其中正确的 | 0 | — |
| 自动入历准确率 | **0%** | **100%**（0 个错误写入） |
| 因「时间已过」拦截 | 0 | **40** |

## 修复后的完整画像

```
总计 89 封真实邮件
预筛过滤:        46 封（营销、自动回复、验证码、无事件线索）
进入规则抽取:    43 封
规则候选:        42 个
  ├─ 因「时间已过」拦截: 40 个
  ├─ 可自动入历:          0 个
  └─ 需审核:             42 个
```

**待审原因分布**：

| 数量 | 原因 |
|---|---|
| 40 | 时间已过（早于当前时刻，不建议入历） |
| 2 | 同一文本内存在多个候选时间 |

## 这份数据无法证明什么（诚实说明）

**这 89 封邮件里没有一个「未来的事件」**，因此这次验证只能证明
「抽取层不会做出危险动作」，**不能证明**「抽取层能正确识别未来的事件」。

原因很实际：这批邮件最晚是 8 月下旬收到的，内容全部已过期。

要验证后一半能力，需要满足其一：

1. 等新邮件到达（正常使用即可自然积累）；
2. 向该邮箱发几封含未来时间的测试邮件；
3. 用合成语料补齐（已做，见 [eval-report.md](eval-report.md)，但那验证的是
   我的假设而非真实分布）。

**这一项后来补上了**：转发进来一封含明确未来时间的真实邀请函，
一次性暴露 8 个缺陷（见下文「第三轮」）。

这是「自动入历准确率」这个指标的价值所在：**它天然偏向保守**。宁可
「0 个自动入历」也不要「1 个错误入历」——前者只是少用了一个功能，
后者会污染用户的日历且用户可能长期不会发现。

## 其他真实数据观察

* **预筛器过滤掉 46/89 封（52%）**，主要是营销推广、自动回复、验证码。
  这是省 token 的关键：LLM 只对剩余部分中的少数邮件调用。
* **两份 Zoom 会议邀请**（同一会议重复投递）被正确识别：第二份入库时
  标记为 `duplicate_of`，`extract_status=done`，**不重复抽取**。
* **繁体中文**（「入境事務處」「上午11時15分」）解析正确。
* 真实 ICS 里 `ORGANIZER` 带 `CN=` 参数，解析后正确提取出邮箱地址。

## 结论

**P2 的门控以「不做出危险动作」为准而非「抽得多」。**

* ✅ 0 个错误的自动入历（这是硬要求）
* ✅ 语义正确的抽取（42 个候选的人类可读性已逐个人工确认）
* ✅ 历史邮件不会污染日历
* ⚠️ 「识别未来事件」的能力**尚未在真实数据上验证**，需要新邮件到达后复验

因此 P3（审核队列）可以开工：审核队列的价值正是处理这 42 个待审候选，
而它们目前 100% 需要人工判断——这恰好说明审核队列是必需的而非可选的。

# 第二轮真机验证（P5 阶段，同一批 89 封邮件）

P5 做摘要时，39 条待审事件几乎淹没了输出——**这暴露了一个此前未处理的噪音源**。

## 发现的缺陷：免责声明脚注被当成事件

### 现象

审核队列里 25 条候选中，大量是同一段文字反复出现：

| 抽出的内容 | 重复次数 | 实际是什么 |
|---|---|---|
| `2025-12-15` 「^截至…App Store 评分」 | **7 次** | 银行邮件脚注 |
| `2025-12-31` 「\*作为香港首间数字银行，截至…用户人数…」 | 多次 | 银行邮件脚注 |

摘要是用来「扫一眼就知道要处理什么」的，被这些噪音淹没后就失去了意义。

### 根因

这些日期出现在**以脚注标记开头的段落**里：

```
*作为香港首间数字银行，截至 2025 年 12 月 31 日，ZA Bank 的用户人数…
^截至 2025 年 12 月 15 日的 App Store 评分。
```

它们是**营销宣称**，不是用户的任何事件。而每封银行邮件都带同一段，
所以同一指纹反复出现。

原有的清洗只处理了**尾部连续**的营销块，没处理这种夹在正文中间、
带脚注标记的段落。

### 修复

新增脚注段落判定（`is_footnote_paragraph`）：段落以
`*` / `^` / `†` / `注：` 等标记开头，或含「资料来源/仅供参考/详见条款」
等免责用语**且段落较短**（脚注通常很短，长段落更可能是正文）→ 不抽取。

### 效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 抽出候选总数 | 40 | **27**（−33%） |
| 「App Store 评分」重复 | 7 次 | **0** |
| 真实事件（预约、到期、面试） | 全部保留 | **全部保留** |

修复后的待审列表里，每一条都是真实邮件内容：入境处预约、域名到期、
转账时间、迎新日报名。

## 一个刻意保留的行为（不是缺陷）

阿里云的「域名到期提醒」出现 3 条（#1/#7/#8），指向**同一个到期日**。
查证后确认这**不是重复抽取**：三封是不同日期发出的**不同邮件**
（内容哈希不同、Message-ID 不同），只是都提醒同一个到期日。

它们指向同一件事，因此指纹相同——这是正确行为。但审核时看到 3 条相同项
仍有轻微困扰，属已知限制（见下）。

## 已知限制（记录而非现在修）

| 限制 | 说明 | 影响 |
|---|---|---|
| 同事件多封提醒不合并展示 | 阿里云连发 3 天提醒同一到期日 → 3 条同指纹候选 | 审核时需自行识别为同一件事 |
| 标题可能残留断句 | 剥离时间后可能留下「（由 起生效）」这类片段 | 审核界面有 evidence 与原文可判断 |
| 摘要里待审最多列 25 条 | 历史积压较多时不会全列 | 用 `events list` 查看完整列表 |

第一条是唯一真正影响体验的：它需要「按 fingerprint 聚合成一组」的展示逻辑，
属于审核界面的增强，不影响正确性（不会误入历）。

# 第三轮真机验证：第一个真实未来事件

> 2026-09-15 · 用户转发进来一封**含明确未来时间**的大学升旗礼邀请函。
> 这是第一次用真实邮件检验「能不能正确识别未来的事件」——前两轮都只能证明
> 「不会做危险动作」。
>
> **本文中的机构名与场地已脱敏为泛称**（原文含可识别到个人的身份信息，
> 不随本报告公开）。日期、中文数字写法、排版结构与缺陷分析均保持原样。

## 样本为什么难

这封邮件不是「一句话写明时间」的那种，它把日程排成了**表格**。下面按原结构
重排，仅把机构名与场地换成泛称：

```
慶祝週年升旗禮（示例）

日期

二零二六年十月一日（星期四）

迎迓

上午十時正 | 示例大學 校史館

升旗禮

上午十時三十分 | 中央廣場升旗台

敬希於二零二六年九月二十一日 (星期一) 或之前，填妥網上回條以作登記。
```

三个特征各自都足以击穿当时的实现：**中文数字**写日期时刻、日期与时刻
**分处不同段落**、标题与时间挤在**短行**里。

## 8 个缺陷

| # | 缺陷 | 后果 | 严重度 |
|---|---|---|---|
| 1 | 中文数字日期（`二零二六年十月一日`）不识别 | 整类中文正式通知全漏 | 高 |
| 2 | 中文数字时刻（`上午十時三十分`）不识别 | 时刻全丢 | 高 |
| 3 | 转发头部（`发送时间: …`）未剥离 | 抽出发送时间假事件，并误导预筛 | 中 |
| 4 | 括号里星期几当独立日期 | **凭空造出错误日期**（10-01 → 09-17） | 高 |
| 5 | 预筛按「全文含日期+时刻」推断规则能覆盖 | 表格排版下规则配不上，LLM 被跳过 | 高 |
| 6 | 时刻槽按 **UTC 小时**分组 | LLM 抽对的 10:30 被静默丢弃 | **最高** |
| 7 | 「短且无标点」当营销页脚 | 日程行是**唯一时刻来源**，却被整段删掉 | **最高** |
| 8 | 全天事件用 UTC 日期、`end` 非开区间 | 截止日在日历上**早一天** | 高 |

### 缺陷 7 是最隐蔽的一个

邀请函把日程排成短行（`升旗禮` / `上午十時三十分 | 中央廣場升旗台`），
这形态与「公司名/地址/电话」完全一样。原先的页脚剥离只看「短且无标点」，
于是把这些行当噪音删了——**清洗阶段的静默数据丢失**，前面所有抽取逻辑
再怎么对都无济于事。

修法是加一条硬约束：**含日期或时刻的行一律视为正文**，且整块剥离必须有
营销词（退订/©/版权所有…）背书。取舍很明确：

> 漏删一段页脚只是噪音，删掉日程是**信息丢失**。

### 缺陷 6 与 7 是同一类错误

两者都是「在某个中间步骤静默丢弃了正确的抽取结果」，而且**单元测试都过**——
因为它们各自只测了局部，没有测「真实邮件走完全程后还剩什么」。
这正是真实样本不可替代的地方。

### 缺陷 8 是同一家族的第三次出现

「UTC 字符串直接当本地时间用」在这份代码里出现了三次
（时刻槽分组、兄弟判定取数、全天事件日期）。第三次是往前端走的时候被发现的：
修复后按新逻辑写真实日历，发现「9-21 截止」落在 9-20。

## 修复后的结果

三个真值事件**全部命中**，时间与标题都正确：

| 事件 | 时间 | 来源 | 状态 |
|---|---|---|---|
| 慶祝週年升旗禮（示例，机构名已脱敏） | 10-01 10:30 (HKT) | llm 0.95 | pending |
| …升旗禮（迎迓） | 10-01 10:00 (HKT) | llm 0.90 | pending |
| 敬希 二零二六年九月二十一日 或之前，填妥網上回條以作登記 | 09-21 全天 | rules 0.85 | pending |

三条都进**待审**，符合「LLM 恒待审 + 规则未过 0.85 严格阈值」的规格。

## 全天事件的时间语义（实测校准）

修复缺陷 8 时，用真实 API 探针确认了两件事（都写进了测试）：

1. **`start.date` / `end.date` 是日历侧的「当地日期」，不是 UTC 日期。**
   我们库里的 `start_ts` 一律是 UTC 瞬时；当地 09-21 零点存成
   `2026-09-20T16:00:00Z`。因此全天事件不能用 `ts[:10]` 取日期，
   否则「9-21 截止」会显示成 9-20——早一天。
2. **`end.date` 是开区间**：Google 只显示 `[start, end)`。
   实测 `start=end` 会被服务端原样接受并存回同一天，即**零长度事件**；
   要表示「10-01 这一天」必须写 `end=10-02`。

因此全天事件的日期换算必须 start/end 联动，不能各自独立地取日期。

## 这份样本仍不能证明什么

它是**自己转发给自己**的一封邀请函，不是正常投递路径的邮件；也只是一封。
因此它能证明「这类中文正式通知能正确处理」，**不能证明**召回率。

真实召回率仍需要靠日常使用自然积累样本。但至少现在可以说：
**「未来事件」这一半能力有了第一个真实证据**，不再是「未验证」。

## 回归测试

本轮所有修复都有回归测试，集中在 `tests/test_forwarded_mail.py`
（37 个用例，每个用例的 docstring 引用真实症状）。其中 6 个专门锁定
「不得因这些修正而过度抽取」——修正漏抽最怕的是反手引入过抽。

# 第四轮：抽取复盘（`automail audit`）

> 2026-09-15 · 为了让「发现缺陷」这件事不再依赖偶然，加了一个每日复盘功能。
> 它上线当天就抓出了 2 个真实缺陷，也暴露了复盘**自身**的 3 次误报。

## 为什么需要它

前三轮的缺陷都是**偶然撞到**的：某封邮件恰好转发进来，恰好触发了某条路径。
这种方式不可持续——用户不会为了测我的脚本而特意转发邮件。

复盘把这件事变成例行公事：每天回看最近 24 小时收到的邮件，主动找出
**可能没抽对**的那些。重点不是「抽错了」，而是**「静默漏掉」**：预筛判定
值得抽取、之后却没产出任何候选，流程照常报成功。

## 它抓到的缺陷

### 缺陷 9：英文月份名日期完全不被识别

Zoom / Google / Outlook 的邀请函写作

```
Date & Time

Aug 28, 2026 12:00 PM Hong Kong SAR
```

只认中文与阿拉伯数字日期的实现，对这类邀请函**整类漏抽**。复盘指出
邮件 #27 预筛放行、零候选、零事件——手动一看，日期就明晃晃在那。

修复时还踩了一个坑：月在前模式 ``Aug 28`` 会从 ``28 Aug 2026`` 里匹配出
``Aug 20``（把年份前两位当日）——**一个凭空的错误日期**，比漏抽更危险，
因为它会静默写进日历。加数字边界后修正。

### 缺陷 10：预筛宣称「可解析 ICS」而实际没有 ICS 部件

这是**最坏的一种组合**：预筛看到 ``has_ics`` 标志为真，判定「含 ICS 部件，
可直接解析」→ **跳过 LLM**；而实际 ``ics_parts`` 为空 → 规则也无从解析 →
整封邮件静默产出零候选。

不是假想：库里只存清洗后的正文片段（隐私设计），**从不存 ICS 原文**，
而标志会保留——因此**离线重跑时每封 ICS 邮件都是这个状态**。实测 #27/#33
均如此。修正为按「真的有可解析部件」判断，而不是按标志。

### 缺陷 11：改进日期识别后，标题反而退化成残句

这是**我自己引入的回归**，由复盘发现（#12/#16 的事件数对不上）。

英文日期能被解析之后，规则从长句正文里派生的标题是
``In addition you are invited to join our…`` 这类**截断残句**；而此前这些
邮件是交给 LLM 的，标题干净（``Registration Deadline: …``）。退化的原因
是去重按「来源优先级」保留规则结果，而规则恰好说不出这是什么事件。

修正分两步：标题退化成残句时改用**主题**（并剥掉 ``[Important Reminder]``
这类机器标记与主题里夹带的日期）；去重时若胜者说不出事件名而败者说得出，
**时间取胜者、标题取更具体者**。

### 附带：重复事件（只写不删）

复盘比对「当前代码的候选」与「库中事件」时发现同一封邮件的**同一时刻有两
条**。根因是重跑抽取只写不删：标题变了 → 指纹变了 → 新条目插入而旧条目留下。

修复加了孤儿清理，但**保护人的决定是硬约束**，因此只有同时满足
「状态仍 pending + 人未手改 + 未写入日历 + 无已派发的延迟窗口」才删。
已批准、已推送、人改过的**一个都不碰**，只计数上报。另有测试专门锁定离线
重跑不得删除 LLM 结果——离线规则无法复现它们。

## 复盘自身的三次误报（都已修正）

报告一旦充满假警报，使用者就不再看了，功能等于失效。因此**误报比漏报更
需要修**：

| 误报 | 原因 | 修正 |
|---|---|---|
| 15/16 个可疑项都是「未配置 LLM」 | 那是**一个全局配置状态**，不是 15 封邮件各自的毛病 | 单列「未判定」并在报告头部说明一次 |
| 凡 LLM 抽过的邮件都报「库中结果已过时」 | LLM 输出每次都不完全一样，比对两次 LLM 结果没有意义 | 过时判定只比较确定性来源（规则/ICS） |
| #92 报「库中缺少全天事件」 | 离线重跑看不到「同日有定时则取代全天」的跨来源合并 | 本轮没调 LLM 而库中有 LLM 事件时，跳过该判定 |
| 5 个通知类邮件报「很可能漏抽」 | 已经问过 LLM、它也说没有——那我们就没有证据说漏了 | 降级为「值得留意」 |

最后一条尤其值得记下来：**「我们主动放弃了最会判断的来源」才是真正该看的
情况**。已问过 LLM 且它说没有，与「没问 LLM 就断定没有」，风险完全不同。

## 这份结果仍不能证明什么
