# 规格五：MIME 解析与正文清洗

> 对应实现 `src/automail/mail/{charset,headers,mime}.py`。
> 本文记录清洗的**功能性理由**，以及实现中踩到的真实陷阱。

## 1. 清洗为什么是功能性的，不只是美化

邮件正文里通常带有：

* 被引用的**旧邮件**（含有错误或过期的日期）
* 很长的**营销页脚**（含有促销截止日、活动日期）
* 邮件客户端的**免责声明**
* **签名档**（含有电话号码，会被误当日期）

若不清理，规则引擎与 LLM 都可能从这些位置抽到过期日期，并在日历上
创建一个**已经过去**的事件。因此清洗顺序是刻意设计的功能，不是格式美化。

## 2. 清洗顺序（不可随意调整）

```
1. 剥离控制字符 / ANSI 转义，统一换行（CRLF/CR → LF）
2. 丢弃免责声明之后的所有内容
3. 丢弃签名之后的所有内容
4. 丢弃引用旧邮件之后的所有内容     ← 防过期日期的关键步骤
5. 删除 `>` 引用行（即使没有标准引用头）
6. 删除尾部营销页脚块
7. 折叠多余空行与行尾空格
```

**第 1 步必须在截断之前**：ANSI 序列可以插入到标记词中间，若先做截断，
`在 2026年9月1日 写道：` 这类标记会被控制字符打断而无法识别，截断失效。
这既是安全问题（终端注入），也是功能问题（清洗被绕过）。

第 2–4 步都是**截断型**：一旦命中标记，其后内容整体丢弃。理由同样是这些区块
都在正文之后，且是过期信息的主要来源。

第 6 步只在**尾部连续区块**上生效，且有两个必须同时满足的条件：

1. 从最后一段向上看，段落要「像页脚」才继续，遇到正常段落即停。
2. **整块必须至少命中一个营销词**（退订/©/版权所有/隐私政策…）。

第 2 条是实测补上的硬约束。原先只按「极短且无标点」判页脚，结果邀请函
**表格排版的日程行**（`升旗禮` / `上午十時三十分 | 中央廣場升旗台`）形态与
「公司名/地址/电话」完全一样，被当噪音整段删掉——而那些行往往是**唯一的
时刻来源**。现在含日期或时刻的行一律视为正文，且没有营销词背书时不做任何剥离：

> 漏删一段页脚只是噪音，删掉日程是**信息丢失**。

正文中间提到「退订」仍不会被误删（有用例覆盖）。

## 3. 实现中踩到的两个 CPython 陷阱

### 3.1 `decode_header` 会把裸非 ASCII 转成字面转义

```python
decode_header("=?utf-8?B?5Lya6K6u?= 通知")
# → [(b'\xe4\xbc\x9a\xe8\xae\xae', 'utf-8'), (b' \\u901a\\u77e5', None)]
#                                                   ^^^^^^^^^^^^^^^^ 字面量！
```

CPython 对**未编码的片段**执行 `encode("ascii", "backslashreplace")`，把裸中文
变成 `\u901a\u77e5` 这样的**字面文本**。仅当头部同时含编码字与裸非 ASCII 时才
走到这条路径，因此极易漏掉——单独测试 `decode_header("通知")` 是正常的。

处理：对 `charset is None` 的字节，若匹配 `\uXXXX` 形态则用
`unicode_escape` 还原（见 `headers._restore_unencoded`）。判据要严格，
避免误伤正文里本来就有的反斜杠。

### 3.2 `getaddresses` 返回的是 `(realname, email)`

```python
getaddresses(["张三 <zhangsan@example.com>"])  # → [('张三', 'zhangsan@example.com')]
getaddresses(["user@example.com"])             # → [('', 'user@example.com')]
```

**第一项是显示名，第二项才是地址。** 记反会让 `From: 张三 <a@b.com>` 解析出
地址「张三」。实现中变量名显式写成 `realname, email_addr` 以防再犯。

另外，垃圾输入会让它返回伪地址（`"not an address at all"` → `('not', 'an')`），
因此解析结果**必须校验含 `@`**，否则脏数据会进入 `senders` 表，
污染「非联系人」判断，进而影响 ICS 自动入历的信任决策。

## 4. 字符集处理

针对国内邮箱的真实情况：

* **声明 GB2312、实际是 GBK 字节**——GBK 是 GB2312 的超集，先试 `gbk`/`gb18030`。
* **latin-1 类"万能字符集"放在候选末位**——它能解码任意字节，放前面会掩盖真实编码。
* 全部失败时用 `charset-normalizer` 检测，最后才用 `replace` 兜底：
  宁可留下替代字符，也不要因解码失败丢掉整封邮件。

## 5. 正文留存与哈希

* 落库的只有**清洗后**的片段，受 `EXCERPT_MAX_CHARS=4000` 限制；
* `body_sha256` 基于**清洗前的完整正文**计算。

第 2 点很重要：哈希必须基于完整正文，否则同一封邮件在「截断」与「未截断」
两种处理下会得到不同哈希，去重与 UIDVALIDITY reactivate 都会失效。
有用例专门断言 `truncated.sha256 == full.sha256`。

## 6. ICS 部件收集

* 同时支持内联 `text/calendar` 与 `.ics` 附件（含 `Content-Type` 不规范、
  仅靠扩展名识别的客户端）；
* 同一封邮件多个 `VEVENT` 都保留，交由抽取层处理；
* 附件与内联同 `UID` 时在抽取层去重。

## 7. 测试覆盖

`tests/test_mail_parsing.py` 60 个用例，覆盖：GB2312/GBK 缺陷、latin-1 顺序、
RFC 2047（含中英混合与 GBK 编码）、无/畸形 Message-ID、`References` 链、
各种地址形态与垃圾输入、HTML-only、quoted-printable、base64、多字符集、
截断与哈希一致性、只有附件、畸形 MIME 缺陷记录、清洗的每一步
（引用/签名/免责声明/营销页脚/正文中的「退订」）、ANSI 剥离、ICS 收集。
