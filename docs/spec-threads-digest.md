# 规格六：线程重建

> 对应实现 `src/automail/threads.py`。
> 这是 v1 的唯一线程能力：**只建图，不做提示**。
> 「可能需要回复」判断属 v2（见文末）。

## 1. 为什么必须客户端重建

163 **不支持服务端 THREAD 扩展**（RFC 5256）——实测 capability 里没有它。
因此线程只能自己算。同理也没有 `IDLE`，所以线程状态更新只能靠轮询后重建。

## 2. 算法（取自 notmuch / mu 的实践）

### 2.1 父节点选择：取最接近本封的已知祖先

优先 `In-Reply-To`；否则遍历 `References` 链，选**深度最大**的已知祖先。

为什么不能只取 `References` 首项：首项通常是**线程根**，而我们要挂到
**最近祖先**上。链条更长的一侧代表更近的关系——notmuch 正是这么做的。

### 2.2 幽灵节点

子邮件的父级尚未入库时，为那个**缺失的 Message-ID** 建一个稳定锚点，
使共享同一缺失祖先的邮件聚在一起。

真身到达后自然并入——因为查找键就是它自己的 Message-ID，不需要特殊的
「合并」逻辑。重建时重新扫描，真身已在库里，自然就位。

实测：89 封邮件里识别出 **8 个幽灵锚点**。

### 2.3 无 Message-ID 的邮件用内容哈希兜底

国产邮箱常见缺 `Message-ID`。**不能丢弃**——丢弃会让这些邮件全部变成
孤立线程（每封一个），线程功能形同虚设。

用内容哈希（`sha256:` 前缀）做键：同一封邮件重复同步时仍落在同一线程。

实测：89 封里有 **11 封**无 Message-ID。

### 2.4 循环引用

按时间顺序处理，父链上做已访问检测。真出现环时取最早的那封为根，
不无限递归。

### 2.5 方向判定

靠 `from_addr` 是否属于用户自己的地址集合。

**未配置用户地址时一律返回 `in`**：宁可把方向判成「收信」，也不要凭空
声称用户发过信——后者会让 v2 的「等回复」判断全部出错。

## 3. 弱关联：为什么必须排除自动化通知 ★

有些客户端不维护 `References`，只保留主题（`Re: xxx`）。这类只能靠
**规范化主题**关联，标 `link_strength='weak'`。

### 3.1 真实数据暴露的问题

第一轮实现后，最大的「线程」是 9 封的弱关联。逐一检查发现它混入了：

* 阿里云域名到期提醒（周期性推送）
* 新设备登录提醒（安全通知）
* ZA Card 交易通知（银行推送）

**它们不是对话**——没有任何人在其中交流，只是同一发件人的定期推送。

### 3.2 为什么这比不合并更糟

把周期推送合成「线程」的后果不是中性的。v2 的「等回复」判断会说：

> 这个线程有 5 封邮件在等你回复

而**实际上无人可回**。这会让用户去翻一个根本不存在的对话，
比不合并成线程更糟糕。

### 3.3 判据

自动化通知不参与主题合并：

* `Auto-Submitted` 头存在（自动回复、自动转发）
* 主题含通知类关键词（提醒/通知/账单/回执/notification/reminder/…）

各自独立成线程，如实反映「这是一条推送，不是一段对话」。

### 3.4 效果

| 指标 | 排除前 | 排除后 |
|---|---|---|
| 弱关联线程 | 5 | **2** |
| 线程总数 | 70 | **74** |
| 最大线程 | 9 封（混合了通知） | 9 封（同一申请流程，合理的弱关联）|

剩下的 2 个弱关联是合理的：某大学申请系统的系列通知（确实同属一个申请
流程）、ZA Card 同主题交易通知。

### 3.5 强关联不参与弱合并

已有 `In-Reply-To`/`References` 线索的线程不参与主题合并，其
`link_strength` 也不会被弱合并降级为 `weak`。

## 4. 为什么全量重建而不是增量

全量重建的结果**只取决于输入**，因此：

* 不会随运行次数漂移
* 不需要「幽灵变真身」的专门合并逻辑
* 不需要维护增量游标

代价是每次重建会重新分配 `threads.id`。v1 不依赖线程 id 的持久性
（`awaiting_since`、`reminded_at` 等字段属于 v2 的「等回复」功能），
因此这是划算的取舍。

**等 v2 需要持久化线程状态时**，应改成增量重建并保留 id 映射——
否则用户的 `snooze`/`mark-replied` 操作会在每次重建后丢失。

## 5. 建图范围

只取 `is_canonical=1`（非副本）且 `stale=0`（未失效）的邮件。

副本与失效记录参与建图只会制造重复线程——UIDVALIDITY 变化后旧记录会
被标 `stale`，它们的内容通常已由 reactivate 后的新记录代表。

## 6. v1 不做的事

**「可能需要回复」判断属 v2。** 它需要：

* 可靠的方向判定（依赖用户地址配置）
* `weak` 关联必须排除在结论之外
* 排除 noreply / 列表 / 自动邮件
* 超时阈值（`REPLY_THRESHOLD_HOURS=24`）
* 人工修正入口（`ignore`/`snooze`/`mark-replied`）

且提示语必须是「**可能需要回复**」而不是「需要回复」——这是猜测，
不是事实。
