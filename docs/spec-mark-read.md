# 规格八：已读回写（唯一的邮箱写操作）

> 对应实现 `src/automail/read_state.py` 与命令 `automail mark-read`。

## 0. 为什么需要单独一份规格

v1 的同步全程只读：`EXAMINE`（只读选中）+ `BODY.PEEK[]`（不改已读状态）。
**已读回写打破了这条性质**，是本项目第一个、也是唯一一个对邮箱的写操作。

写别人的邮箱比写自己的数据库危险得多：数据库删错了可以重建，邮箱状态改了
会立刻影响使用者每天看到的界面，而且**误标会让一封需要处理的邮件从「未读」
里消失**——这正是这个功能要解决的问题，弄错方向反而更难发现。

因此这份规格的每一节都在回答同一个问题：**什么情况下我们决定不写？**

## 1. 目标（一句话）

让「未读」继续表示「需要你处理」，而不是被已处理的邮件占满。

## 2. 三道闸门

| 闸门 | 作用 |
|---|---|
| **默认关闭**（`MARK_READ_POLICY=off`） | 升级既有安装不得静默改变邮箱状态 |
| **默认 dry-run** | `automail mark-read` 只报告；`--apply` 才发 STORE |
| **UIDVALIDITY 一致** | 不一致时 UID 已重新分配，继续写会标到**别人的邮件**上 |

第一道尤其重要：这是一个会改变外部状态的功能，**不能靠"默认开启"来被发现**。
使用者必须主动读文档、主动开启。

## 3. 窄接口

后端只暴露一个写方法：

```python
def mark_seen(self, uids: list[int], *, seen: bool = True) -> None:
    """只改 \Seen。不能删邮件、不能移动、不能改别的标志。"""
```

刻意不提供 `delete` / `move` / `set_flags(任意标志)`。接口窄到**没有能力**
做别的事，比靠调用方自觉更可靠。

对应地，判断 STORE 是否合法只有一条：**文件夹必须以可写方式选中**
（`select_folder(readonly=False)`，即 `SELECT` 而非 `EXAMINE`）。只读选中时
服务端会拒绝 STORE——这层保护让我们"忘了切写模式"成为**显式报错**而不是
静默无效。

## 4. 什么算「处理完」

```
off        不写
resolved   只在没有任何事件等你处理时写（推荐）
processed  所有抽取完成的邮件都写
```

`resolved` 的两道保守判断：

### 4.1 事件状态

仍处于这些状态 → **保持未读**：

| 状态 | 为什么 |
|---|---|
| `pending` | 等你审批 |
| `uncertain` | 反查失败，无法判定日历侧状态，需要确认 |
| `push_failed` | 推送失败，需要关注 |

其余状态（`approved` / `pushed` / `rejected` / `ignored` / `cancelled` /
`superseded`）都表示你的那部分已做完，或事件已被程序妥善处理。

### 4.2 措辞上像待办

**这一条是实测补上的。** `resolved` 的判据是「没有待处理的**日历事件**」，
但「没有日历事件」不等于「没事要做」：

> GitHub 的仓库邀请 `X invited you to X/repo` 不产生任何日历事件。
> 按「无事件 → 已处理」的判据会被标为已读——而它显然需要你回应。

因此再补一道检查：主题或发件人命中「邀请/确认/回复/截止」等信号词时，
保持未读（`_ACTIONABLE_SIGNALS`）。

两个刻意的设计选择：

* **只扫主题与发件人，不扫正文**。正文里「如有疑问请联系」「confirmation」
  这类词太普遍（收据里到处都是），扫正文会让几乎所有邮件都被判为待办，
  这道闸门等于失效。
* **词表偏宽**。漏标只是少省一件事，误标会藏起待办——方向不能反。

`processed` 不加这道筛选：使用者明确选择「抽取完就标」，就该照办。

## 5. 可回退

`mark-read --undo` 把**本程序标记过**的邮件恢复为未读。

判定依据是 `messages.marked_read_at`——它只在我们的写操作成功后写入，
与 `flags` 列刻意分开（后者反映服务端当前状态，可能是你在别的客户端读的）。

因此回退**不会碰你自己读过的邮件**：那属于你的动作，不该被我们撤销。

有回退路径才敢开这个功能。

## 6. 幂等与记账

| 情况 | 行为 |
|---|---|
| 服务端已是 `\Seen` | 不发 STORE，计入 `already_seen` |
| 本程序标记过 | `marked_read_at` 非空 → 后续轮次跳过 |
| 单批失败 | 不放弃整轮，计入 `failed` 并记录原因 |

「已是已读」与「将标记」分开计数是必要的：dry-run 若把两者合并报成
「将标记 55 封」，而其中 52 封本来就已读，会让这个唯一改变邮箱状态的操作
显得比实际激进得多。**报告的数字必须诚实地反映实际会发出的 STORE。**

## 7. 与定时任务的关系

启用后，`automail run --apply`（默认每 30 分钟）会**自动执行**已读回写。

这意味着改完 `.env` 就等于授权它在后台整理邮箱，不再逐次确认。这是刻意
的——否则功能形同虚设。使用者在开启前应当知道这一点，README 里有醒目提示。

想先人工复核，就不要走 `run`，只手动跑 `mark-read`。

## 8. 允许失败

单封/单批 STORE 失败不该让整轮致命：邮箱问题多为暂时性（风控、网络），
下次运行会重试。但**必须计入报告**，否则「有多少没标成功」对使用者不可见。

文件夹级失败（选中失败、UIDVALIDITY 不符）记入 `skipped_reason` 或 `error`，
并让命令以 `EXIT_PARTIAL` 结束。
