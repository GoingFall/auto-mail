# 真实 Google 日历验证报告

> 2026-09-15。授权成功后的端到端验证：**全部机制在真实 API 上确认有效**。
> 这填补了 P3 阶段的一个缺口——那时只能用 `FakeCalendar`。

## 为什么要做这轮验证

P3 的所有写入安全机制（幂等反查、三方比对、冻结、归档）都是在
**`FakeCalendar`** 上测试的。假替身有两个根本局限：

1. **它按我的理解模拟 Google 的行为**，而我可能理解错了
2. **它不校验 payload 格式**——真实 API 会严格拒绝不合规的字段

这一阶段反复出现的同类错误（假 IMAP 服务器太宽容、假 flow 绕过 oauthlib
真实校验）说明这不是理论担忧。因此授权成功后立即用真实 API 逐项验证。

## 验证项与结果

| 机制 | 验证方式 | 结果 |
|---|---|---|
| OAuth 授权 | 浏览器授权 + token.json 检查 | ✅ 含 **refresh token**（103 字符），scope 仅 `calendar.events` |
| refresh token 续期 | 令牌已过期后连接 | ✅ 自动续期成功，无需重开浏览器 |
| 只读连接 | `list_events` | ✅ 读到日历中的真实事件 |
| 写入（定时事件） | `dateTime` + `timeZone` 格式 | ✅ Google 接受 |
| 写入（全天事件） | `date` 格式 | ✅ Google 接受 |
| 所有权标记 | 回读检查 `extendedProperties` | ✅ `auto_mail_key` 正确写入 |
| **幂等反查** | 模拟「创建成功但写库前崩溃」 | ✅ **回填成功，未产生重复事件** |
| `privateExtendedProperty` | 按 key 反查 | ✅ 命中（该参数在真实 API 上生效） |
| **哈希稳定性** | 连续 3 次读取同一事件 | ✅ 规范化哈希完全一致 |
| 归档（可恢复） | 置 `status=cancelled` | ✅ 归档后从 `list_events` 消失，事件未硬删 |

### 特别值得记的一点：哈希稳定性

连续三次读取同一事件，规范化哈希完全一致（`7dc293d1…`）。
这验证了 `benign_evolution`（无害演进）分支在真实 Google 上成立。

**如果这一步失败，后果很严重**：每次检查都会认为「远端有改动」，
进而可能误判为用户手改，导致所有事件被冻结——功能完全不可用。

真实数据印证了这里的关键细节：Google 把描述里的 `\n` **折叠成了空格**。
这正是 P3 阶段修的那个空白折叠 bug（当时只折叠 `[ \t]+`，保留了换行）。
若没修，哈希会不稳定，机制直接失效。

## 发现的问题：FakeCalendar 演练污染真实数据库

P3 用 `FakeCalendar` 演练时，虚拟事件 ID（`evt-1`）被写进了**真实数据库**。
切到真实后端后，这些记录指向不存在的事件。

**影响有限**（`PushEngine` 遇到这种情况会走 `NOT_FOUND_POLICY` 转人工，
不会静默出错），但属于数据卫生问题，已清理。

**教训**：演练应使用独立的数据库（或至少演练后清理），
不要让 `--backend fake` 的产物留在生产库里。

## 当前状态：0 个可推送事件（这是正确的）

29 个待审事件**全部是过期时间**（8 月的域名到期、银行交易通知等），
按设计就不该写入日历。因此 `push --approved` 处理 0 条。

这暴露出一个需要说清楚的能力边界：

| 能力 | 验证状态 |
|---|---|
| **不做出危险动作**（不误写、不覆盖用户改动、不重复） | ✅ 已在真实数据 + 真实 API 上充分验证 |
| **正确识别未来的事件** | ⚠️ 仍未有真实样本验证 |

原因：那 89 封邮件最晚是 8 月下旬收到的，内容全部已过期。
「时间已过 → 待审」规则会拦截它们，所以 29 个候选都停在待审。

**要验证后一半能力，需要含未来时间的真实邮件到达**（正常使用即可自然积累），
或向该邮箱发几封测试邮件。

## 结论

P4 完成：真实 Google Calendar 接入的**全部机制已在真实 API 上验证有效**。
系统的安全性（不误写、不覆盖、不重复）有充分证据；
「识别未来事件」的准确率需要新邮件到达后复验。

## 给使用者的建议

1. **等新邮件到达**——每天的自动同步 + 摘要会自然积累真实样本
2. 收到含未来事件的邮件后，检查 `events list` 里的候选是否正确
3. LLM 未配置时抽取只有规则+ICS；配置后可提升自由文本的识别率

# 补充：启用 LLM 后的抽取对比

> 2026-09-15。填入 LLM 凭据（DeepSeek `deepseek-flash`）并重新抽取后的实测结果。

## 配置与连通性

| 项 | 值 |
|---|---|
| `LLM_BASE_URL` | `https://api.deepseek.com` |
| `LLM_MODEL` | `deepseek-flash`（确认在服务端模型列表中） |
| 发送字段 | `excerpt, subject, received_at, timezone`（**不含**发件人地址；主题经正则脱敏） |
| `response_format=json_object` | ✅ 支持，返回干净 JSON |

抽取请求实测返回：

```json
{"events": [{"title": "面试", "start": "2026-10-20T15:00:00+08:00",
  "location": "B 座 302 会议室", "confidence": 0.95,
  "evidence": "面试定于 2026年10月20日 下午3点，地点 B 座 302 会议室。…"}], "todos": []}
```

## 抽取效果对比

| 指标 | LLM 未配置 | LLM 已配置 |
|---|---|---|
| 预筛过滤 | 46 | 47 |
| 产生候选的邮件 | 26 | **33** |
| 候选总数 | 29 | **42** |
| 来源分布 | rules 29 | rules 29 + **llm 13** |
| LLM 调用 | 0 | **19 次，全部成功** |
| LLM 降级跳过 | 19 | **0** |

**LLM 独立发现 13 个规则完全漏掉的候选**——全是某大学的项目的日程
（开学典礼、报名截止、签证条件截止）。规则漏掉它们的原因是时间表达嵌在
英文自由文本里（`Deadline: by noon, 24 August 2026`、`Ceremony 3:00 pm – 4:15 pm`），
不匹配现有的中文时间模式。

## 发现的真实问题：同一件事被多封邮件重复抽出

13 个 LLM 候选**实际只对应约 5 件真实的事**——开学典礼被 6 封不同邮件
（邀请、提醒、确认、报名确认）各抽了一次。

### 尝试自动合并，结论是不安全

先用真实数据试算「同日期 + 标题相似度」的合并规则，发现**假合并风险**：

| 案例 | 时间 | 标题相似度 | 真相 |
|---|---|---|---|
| ZA Card 消费 #24/#25/#26 | 同分钟 2 条 + 4 分钟后 1 条 | **1.00** | **三笔独立交易** |
| 八達通通知 #18/#19/#20 | 同一天 | **>0.8** | **三张不同卡**（提到不同卡号） |
| 阿里云到期 #1/#7/#8 | 同一天 | **1.00** | **三封不同日期的提醒**（同一到期日） |

**相似度无法区分「同一件事」与「标题相同的不同交易」**——
上面每一条的相似度都是满分。

误合并的代价是**静默丢失真实信息**（丢掉两笔消费、两张卡的操作记录），
比留下重复候选严重得多。因此**放弃自动合并**。

### 改为「只提示不合并」

`events list` 现在会标注「疑似与 #N 重复（相似度 X）」，但：

* **不合并、不隐藏任何候选**——条目数不变
* **不影响可批准性**——被标注的照样能批准（有测试守护）
* 提示文字明确说明它在提示什么、以及为什么不能自动合并

实测效果：阿里云 3 连发、入境处预约 2 条被正确标注；
而 ZA Card 三笔消费**没有**被误标（LLM 生成的标题措辞略有不同）。

## 能力边界的当前状态

| 能力 | 状态 |
|---|---|
| 不做出危险动作（不误写/不覆盖/不重复） | ✅ 真实数据 + 真实 API 充分验证 |
| 识别**自由文本**中的事件 | ✅ LLM 独立发现 13 个规则漏掉的候选 |
| 识别**未来**事件 | ⚠️ 仍无真实样本 |
| 同一件事的跨邮件归并 | ⚠️ 只提示不合并（自动合并已验证为不安全） |

当前 42 个候选中，**39 个是已过期时间**（按设计被「时间已过」拦截），
仅 3 个在未来。原因仍是那批邮件最晚 8 月下旬收到、内容全已过期。

**结论**：LLM 显著提升了自由文本的召回（+13 个候选），
但没有改变「缺乏未来样本」这个验证缺口——那需要新邮件到达。
