# 规格九：图形界面

> 对应实现 `src/automail/gui/`、`src/automail/gui_main.py`。
> 命令：双击 `auto-mail-gui.exe`（或源码 `python -m automail` + `AUTOMAIL_GUI=1`）。

## 0. 三条不可违反的约束

写界面的过程中反复撞到同一类问题，因此先把结论摆在最前面——**它们都不是风格
偏好，违反任一条都会造成用户可见的故障**。

### 约束一：Tk 只能由主线程操作

后台线程直接改控件会**随机崩溃**（不是每次都崩，因此极难复现）。

实现方式：后台线程只往队列里放事件，主线程用 `after(100ms)` 取出来渲染
（`gui/app.py` 的 `_poll`）。`Worker` 的进度回调也只做入队
（`gui/worker.py` 的 `reporter`）。

### 约束二：worker 线程是非守护的，但必须能停下来

这两句看似矛盾，各自都有理由：

* **非守护**：守护线程会在主线程退出时被**强杀**，任务中断 → 运行锁无法在
  `finally` 里释放 → 锁滞留到 TTL（默认 30 分钟），期间**所有**运行
  （含计划任务）都报「已有运行在进行中」。
* **必须能停**：非守护线程会**阻塞解释器退出**。实测挂死过一次——最初的实现
  用阻塞式 `queue.get()`，线程永远卡在那里，`shutdown()` 放进队列的信号也
  看不到，进程再也退不掉。

解法：`get(timeout=...)` 轮询 + 停止标志；`shutdown()` 只**请求**停止
（等当前任务跑完），并用 `atexit` 注册一次兜底。关窗时若任务在跑，给出
「完成后退出 / 继续在后台」两个真实可选的选项，**不提供强杀**。

### 约束三：配置改动必须重建依赖 settings 的对象

`Pipeline` 在**构造时**就绑定了 settings 实例。只替换 `AppState.settings`
而让旧对象继续用旧配置，会出现「设置显示已保存、实际不生效」——最难查的
一类问题。因此 `AppState.reload_settings()` 之后的所有使用方都必须重建。

## 1. 分层（为可测性而分）

```
gui/state.py       数据与配置，无 Tk    ← 可用普通单测覆盖
gui/worker.py      线程与队列，无 Tk    ← 可用普通单测覆盖
gui/viewmodels.py  纯函数整形，无 Tk    ← 可用普通单测覆盖
gui/app.py         主窗口（唯一碰 Tk 的地方之一）
gui/panels/*.py    各标签页
```

**为什么要把前三层与 Tk 分开**：窗口需要显示会话，CI 与构建机上跑不了。
而最容易出错的东西恰恰在那三层里——时间时区换算、状态标签覆盖、配置重载、
线程语义。分开之后它们在本机与 CI 上都测得到。

反过来，面板层几乎只剩布局代码，出错一眼可见（不像逻辑错误那样隐蔽）。

## 2. 路径锚定（图形界面能跑的前提）

`.env`、`credentials.json`、`token.json`、`data/out/logs` 全部按
**应用基目录**（`app_base_dir()`）解析，**不是进程工作目录**。

命令行一直没暴露这个问题，只因为它的启动器先切了目录
（`auto-mail-run.cmd` 里的 `cd /d "%~dp0"`、`run.ps1` 里的 `Set-Location`）。
图形界面从桌面快捷方式启动时工作目录是别处，于是：

* 读不到 `.env` 与凭据 → 显示"未配置"
* 数据库指向错误的目录 → 实测在 `C:\Windows` 下启动直接报
  `[WinError 5] 拒绝访问: 'data'`

**注意锚定必须在校验阶段做**（`_resolve_relative_config_paths`），不能只靠
`default_factory`：`.env` 的优先级高于默认值，而模板里就写着
`DATA_DIR=data` 这类相对路径。有测试断言 `_PATH_FIELDS` 覆盖了全部 Path 字段。

## 3. 凭据存储

`secrets_store.py` 用 Windows DPAPI（ctypes 调 `crypt32`，零新依赖）加密
`data/secrets.dat`，密钥绑定当前 Windows 用户。

**威胁模型要说清楚**：同用户态下任意进程都能解密——DPAPI 的固有边界。
它防的是文件被拷走/被同步/被误分享，**不防**本机已被同用户执行的恶意代码。

优先级：**环境变量 → `.env` → 加密存储**。`.env` 优先是刻意的逃生通道
（加密文件损坏或换机器时，直接改 `.env` 就能救回来）。

### 空值语义（踩过的坑）

`.env` 里的 `IMAP_AUTH_CODE=`（空值）**必须当作"未设置"**，否则它会**盖住**
加密存储里的真值。迁移恰好会制造这种空值行，于是出现"迁移报告成功、但新会话
读到长度 0"。因此 `Settings` 设了 `env_ignore_empty=True`。

### 明文迁移

已有用户的密码明文放在 `.env` 里。迁移顺序是**先验证后擦除**：

1. 读出 `.env` 明文（只读）
2. 加密写入 `secrets.dat`
3. **立即解密回读并逐键比对**（写成功 ≠ 读得回来）
4. 只有第 3 步通过，才备份 `.env` 并清空那两个键

任何一步失败都**保留 `.env` 原值**。宁可继续用明文，也不能出现"加密文件写坏
了、明文又被抹了"导致凭据彻底丢失。

只迁 `IMAP_AUTH_CODE` / `LLM_API_KEY`；`token.json` 保持 Google 原生格式
（它由 google-auth 亲自读写，加密会破坏刷新链路）。

## 4. 配置写入（`.env` 改写）

`envfile.py` 是**外科手术式**改写：只替换指定键的值，其余字节原样保留——
注释、空行、顺序、程序不认识的自定义键。不是"读成字典再 dump"，那会丢掉
全部排版。

两个实测踩到的 bug：

* **CRLF 被归一化**：Python 文本模式默认 universal newlines，会把 `\r\n`
  折成 `\n`。写回去就把使用者的 CRLF 文件全变成 LF（Git 看来是整文件改动）。
  必须显式 `newline=""`。
* **备份撞名**：文件名只精确到秒时，同一秒内的多次保存会互相覆盖，
  结果是"备份好像有、其实只剩最后一份"。必须带微秒 + 去重后缀。

写入用「临时文件 + `os.replace`」保证原子性（计划任务可能正在读同一个文件）。
重复键**拒绝写入**并报行号，不猜哪个生效。

## 5. 面板与语义

| 面板 | 内容 | 关键语义 |
|---|---|---|
| 总览 | 待审数量、配置状态、立即同步、快捷入口、日志 | 待审数量放最显眼处 |
| 待审事件 | 批准/否决/忽略/修正/接管、冲突与疑似重复标注 | **批准不写日历**，显示「已批准，等待写入日历」中间态 |
| 邮件 | 列表筛选、详情、脱敏正文片段 | 正文只有片段（≤4000 字），界面要说清 |
| 日历 | 今天与未来 7 天 | 无 `htmlLink` 存储，按需拼链接，拼不出退回首页 |
| 复盘 | 很可能漏抽 / 值得留意 / 未判定 | 「未判定」单列，不混进可疑项 |
| 设置 | 凭据、LLM、授权、策略、计划任务 | 密码不回显；保存后重建依赖对象 |

### 批准 vs 接管

被外部修改/冲突/日历中消失的事件处于**冻结态**，状态机不允许直接批准。
界面据此提示「先接管」——若给错按钮，使用者会反复点击却毫无反应。

### 编辑走与流水线相同的解析路径

标题/时间修正沿用 pipeline 的解析与校验，不在面板里另写一份格式逻辑
（两份校验迟早分叉，而这里改错会直接写进日历）。编辑后 `manual_edited=1`
与 `field_provenance=human`，自动流程不会覆盖。

### 冲突与疑似重复都是"读取时派生"

`conflicts_with` / `sibling_ids` / `probable_duplicate_of` 不落库，
因此编辑后刷新列表即自动重算，无需额外代码。

## 6. 暂停自动运行

`pause.py` 用标记文件（`data/AUTOMATED_RUN_PAUSED`）表达状态，**不卸载计划
任务**——卸载了还得记得装回来。

**作用域是刻意的**：只挡计划任务触发的 `run`，不挡图形界面里的手动同步。
点「立即同步」说明使用者现在就想跑一次，与"别在我不知情时自动跑"是两件事。
若连手动也挡，就得先恢复再点，反而多一步且容易忘了恢复。

有测试断言 `Pipeline` **不包含** `is_paused` 检查，防止以后有人顺手加上、
让手动同步变得时灵时不灵。

## 7. 已知限制（如实说明）

| 限制 | 原因 |
|---|---|
| 无法深链到 163 的具体邮件 | 网页 URL 是会话式的（`main.jsp?sid=...`），没有稳定的单封地址。只能打开首页 + 提供「复制主题」 |
| Google 日历链接是"尽力而为" | `htmlLink` 在规范化哈希黑名单里（对内容比对无意义且会造成哈希漂移），未存库；按 `gcal_event_id` 拼链接，失败退回首页 |
| 没有取消机制 | 首次长同步不可中断。强杀会让锁滞留到 TTL，因此只提供「完成后退出」 |
| 托盘需要新依赖 | `pystray` + `Pillow`（Pillow 原本在打包排除列表里）。独立可选，去掉不影响其余功能 |
| 分发体积增大 | Tcl/Tk 数据约 5.5 MB（`_tcl_data` 4.4 MB + `_tk_data` 1.1 MB）。两个 exe 各 15.5 MB，但共用 `_internal/`，因此**不是**翻倍 |

## 8. 打包与构建自检

两个可执行文件**共用同一份 Analysis/PYZ/COLLECT**，差异只有控制台子系统：

* `auto-mail.exe` — 控制台（计划任务据此拿退出码）
* `auto-mail-gui.exe` — 窗口化（双击不弹黑窗）

运行时按可执行文件名分派（`__main__._is_gui_invocation`）。

`build-exe.ps1` 的 GUI 自检 `--selftest` 会**真的建窗口并构建全部面板**，
退出码区分三种结果：

| 码 | 含义 | 构建脚本 |
|---|---|---|
| 0 | 界面构建成功 | 继续 |
| 3 | 本机没有显示会话（构建机常见） | **跳过，不报错** |
| 2 | 真的崩了（含打包缺 Tcl 数据文件） | **失败** |

第 2 与第 3 的区别是必须的：把「打包缺 Tcl 数据文件」当成 headless 跳过，
就会发布一个双击即崩的 exe——这正是本项目在 `unittest`/`httplib2` 上踩过的
同类陷阱（构建成功、`--version` 正常、一用功能就崩）。

## 9. 鼠标滚轮与键盘滚动

Tkinter 对滚轮的默认支持**不完整**，而且缺口位置很反直觉（实测 Tk 8.6.15）：

| 控件 | 内建滚轮 | 内建翻页键 |
|---|---|---|
| `Treeview` / `Text` / `Listbox` | 有（但每格只滚 1 行，偏慢） | 有 |
| `Canvas` | **完全没有** | **完全没有** |

更要紧的是 Tk 的结构性限制：**bindtags 不包含祖先控件**。滚轮只投给指针下的
那个控件及其*类*，不冒泡。设置页用 Canvas 承载整页内容，而输入框占了该页
大部分面积——指针停在输入框上时，事件目标是 `TEntry`，它和它的类都没有滚轮
绑定，事件就此消失，**外层 Canvas 根本收不到**。

两个缺口叠加的结果：**设置页整体不响应滚轮**（无论指针在字段上还是空白处）。

修法不是"给每个控件加绑定"，而是 `scrolling.py` 在 `all` 级别统一拦截，
再沿祖先链找真正该滚的控件：

1. **先清掉内建的类级滚轮绑定**。不清的话内建绑定（先执行）与本模块
   （后执行）都会滚一次 → 每格 6 行。实测表现为"滚太快"，很容易被当成
   个人感觉而忽略。
2. 数值：`Treeview/Text/Listbox` 每格 3 行（贴近平台惯例，内建是 1 行）；
   `Canvas` 每格 1 个单位——实测 Canvas 的 1 个单位 = 视口 1/10（约 60px），
   已接近"3 行"的手感，乘 3 会一次滚掉近半屏。
3. 高精度滚轮/触控板的 `delta` 可能小于 120（甚至为 ±1）。按 `delta/120`
   取整会得到 0 单位 → **看起来完全没反应**，因此不足一格按一格处理。
4. 键盘只接管 `PageUp`/`PageDown`（Canvas 连键绑定都没有）。**方向键不接管**
   ——那在输入框里是移动光标，抢过来会让打字变难受。
5. 控件自己有翻页绑定时**跳过**（否则一次翻两页）。

> 测试注意事项：Tk 窗口**必须已映射**（不能 `withdraw()`），否则不做几何
> 计算、Canvas 尺寸停在 1×1、`yview` 退化，所有滚动断言都会误判成"没生效"。
> 另外键盘事件需要 `focus_force()`——窗口没有真实 OS 焦点时 `focus_set()`
> 不足以让事件被投递。

## 10. 界面首次可用性踩到的坑

这一节的每一条都是**打开窗口就能看见**的问题，但都不是"布局不好看"，
而是让功能实际不可用或损坏数据。记下来是因为它们的共同点：
**单测全绿、代码看着也对**，只有真的把界面打开、按正常方式用一遍才会暴露。

### 10.1 密码框里的"占位提示"会被当成新密码保存（数据损坏）

tkinter 的 `Entry` 没有原生 placeholder，于是把「已配置（留空则不修改）」
塞进输入框，靠聚焦时清掉来模拟。结果是**数据损坏**：

> 使用者打开设置，只想改一下邮箱账号，没去点密码框，直接按「保存配置」
> → 那段中文提示被当作新授权码写入 → **真实授权码被覆盖**。

而且不会立刻报错，直到某次同步失败才发现。

正确做法：状态用**独立标签**显示（`✔ 已配置` / `未配置`），输入框永远真为空。
任何"先塞文本再检测清掉"的方案都有这个风险，不要用。

回归测试读的是**控件真实内容**（`entry.get() == ""`），并断言
「不动密码框保存后 `.env` 里的授权码不变」——比只查源码有效得多。

### 10.2 启动时面板不刷新 → 整个界面是空的

`refresh_all()` 只刷"当前可见"那一页，而启动时**一次都没刷**。于是打开窗口：

* 设置页显示「未配置」（其实已配置）
* 邮件页一片空白
* 总览没数字

使用者的第一印象就是"我的配置没被读到"，然后会去重填一遍。

修法：启动时 `refresh_all(force=True)` 刷全部；并绑定
`<<NotebookTabChanged>>`，切页时刷新那一页（否则看到的是过期数据）。

### 10.3 工作线程调用 `logging` 会崩溃解释器

`Worker._loop` 的异常分支原本写 `logger.exception(...)`。实测**直接崩溃整个
解释器**：

```
Windows fatal exception: code 0x80000003
  Garbage-collecting
  File "<frozen _collections_abc>", line 439 in __subclasshook__
  File "C:\Python313\Lib\logging\__init__.py", line 324 in __init__
  File "src\automail\gui\worker.py", line 131 in _loop
```

后台线程构造 `LogRecord` 时要做 `isinstance` 检查，而主线程正在 GC、动的是
CPython 的 ABC 缓存——两者竞争就崩了。这不是"偶发警告"，它把整个测试运行打断。

修法：工作线程用 `traceback.format_exc()` 把堆栈**当数据**放进
`TaskResult.detail`，由**主线程**统一记录。这同时更符合本模块的架构约定
（worker 只入队，不碰别的）。回归测试用 AST 检查代码里有没有 `logger.*`
调用——**不能用字符串搜索**，因为注释里正解释着"为什么不能记日志"。

### 10.4 停机后提交的任务被静默丢弃，且界面永久"繁忙"

`submit()` 只检查 `busy`。线程已退出时它仍返回 `True`：任务放进队列再也没人取，
而 `_busy` 再也不会被清掉 → 界面从此永久显示"正在运行"，之后每个动作都被
当成"繁忙"拒绝，只能重启程序。

修法：停止标志已设、或线程已不存活时**明确返回 `False`**，让界面能提示
「worker 已停止」。宁可拒绝，也不要静默丢弃。

### 10.5 Tk 变量在根窗口销毁后才被回收

`tkinter.Variable.__del__` 会访问 Tcl（只有 `_tk is None` 时才跳过）。
根窗口销毁后这些变量往往还被控件/面板引用着，等 GC 时才回收——那时可能已不在
主循环里，于是抛 `RuntimeError: main thread is not in main loop`。

修法：`App.register_var()` 登记，`_do_close()` 在 `destroy()` **之前**统一把
`_tk` 置空（tkinter 认可的安全出口）。

### 10.6 测试侧的两个陷阱

* **Tk 窗口必须已映射**。用 `withdraw()` 会让 Tk 不做几何计算、Canvas 尺寸停在
  1×1、`yview` 退化，所有滚动断言都误判成"没生效"——我因此差点把好代码改坏。
  正确做法是放到屏幕外（`+3000+3000`）。
* **键盘事件需要 `focus_force()`**，`focus_set()` 在窗口没有真实 OS 焦点时
  不足以让事件被投递。

## 11. 主线外修复（本轮顺带）

| 现象 | 根因 |
|---|---|
| `stats` 完全不可用 | 中文控制台默认 GBK，邮件主题里的 emoji 让输出抛 `UnicodeEncodeError`。入口统一切 UTF-8 + `errors="replace"` |
| `doctor` 误报「未找到 .env」 | 它硬编码了 `Path(".env")`（相对 CWD），与配置加载用的路径不一致 |
